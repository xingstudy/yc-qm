## 1. 文档边界与优先级

本文定义外部目录的下一阶段能力：企业邮箱与企业微信身份的双向自动关联、企业微信扫码首次登录即时创建成员，以及“仅登录与身份绑定”和“托管组织目录”两种来源模式。

现有《外部目录身份匹配与登录绑定 PRD》记录已经实现的基线能力，继续作为当前线上行为的说明。本文所述能力启用后，如两份文档在以下事项上冲突，以本文为准：

- 未绑定的受管来源用户是否允许首次登录时创建 `organization_users`；
- 外部目录是否允许创建或维护组织节点和成员关系；
- 邮箱缺失时是否允许先创建成员、后补全邮箱；
- 企业邮箱能否作为反向验证企业微信稳定身份的证据；
- 来源模式切换、托管字段归属和离职处理。

在新能力完成迁移并由管理员启用之前，系统保持现有失败关闭行为，不自动改变已配置来源的语义。

## 2. 背景

QM 当前可以同步企业微信成员并以稳定的外部成员 ID 绑定现有组织成员，但实际使用中出现两个问题：

1. QM 组织成员已经有企业邮箱，例如 `lijixing@qfpay.com`、`liuyanwen@qfpay.com`，同步结果仍无法自动匹配，只能由管理员手工绑定。
2. 外部目录目前主要同步身份快照，没有根据企业微信部门和成员关系维护 QM 的“组织架构”。

第一个问题的直接原因不是邮箱字符串不一致，而是当前企业微信通讯录接口在新应用和新授权条件下通常不返回 `email` 或 `biz_mail`。企业微信“获取部门成员详情”接口虽然包含 `biz_mail` 字段，但受权限与历史授权策略限制，不能作为稳定的批量邮箱来源。

企业微信同时提供“邮箱获取 userid”接口。QM 可以用自身已验证的企业邮箱反查企业微信 `userid`，将成功结果作为企业微信侧验证过的稳定身份依据。该接口有可见范围和错误比例限制，因此必须采用增量反查、持久化结果、退避和熔断，不能在每次全量同步或每次登录时无上限地重复调用。

参考接口：

- [企业微信：获取部门成员详情](https://developer.work.weixin.qq.com/document/path/90201)
- [企业微信：邮箱获取 userid](https://developer.work.weixin.qq.com/document/path/95895)
- [企业微信：获取子部门 ID 列表](https://developer.work.weixin.qq.com/document/path/95350)
- [企业微信：获取单个部门详情](https://developer.work.weixin.qq.com/document/path/95351)

## 3. 产品决策摘要

### 3.1 成员与身份模型

- `organization_users` 继续表示组织内唯一的 canonical 人员。
- 登录邮箱、企业微信、OIDC 等均表示该人员可使用的身份，一个人员可以关联多个身份。
- 外部目录身份的稳定键为“供应商类型 + 供应商租户命名空间 + 外部 subject”。企业微信中的 CorpID 和 UserID 分别是租户命名空间与外部 subject 的首个实现，不成为 Core 专用字段。
- 企业邮箱身份的稳定键为“签发方 + subject”；邮箱地址是已验证资料和匹配证据，不直接替代稳定身份键。例如邮箱身份提供方为某用户签发的 subject 在邮箱改名后仍可保持不变，而同一个邮箱字符串在不同签发方下也不是同一身份。
- `organization_users.email` 只是 canonical 人员资料，不能单独证明邮箱所有权。自动反查只读取带 `emailVerified=true` 证据的邮箱/OIDC 身份，并排除当前目录来源自身生成的身份，避免把管理员填写或历史导入的邮箱误当成已验证证据。
- 已验证邮箱证据必须同时记录证据所验证的规范化邮箱值。邮箱发生变化但新值未验证时，必须清除旧证据；不能把“这个身份曾验证过某个邮箱”解释成“当前邮箱已验证”。
- `organization_users.email` 在通用数据模型中允许为空，但支持按需敏感资料授权的企业微信来源不得在首次扫码时创建无邮箱人员；必须先取得可信 `biz_mail`。
- 不根据 `userid` 猜测 `userid@企业域名`，也不因姓名相同自动合并人员。

### 3.2 两种来源模式

每个外部目录来源必须选择一种模式：

1. `identity_only`，Admin 展示为“仅登录与身份绑定”。
2. `managed_directory`，Admin 展示为“托管组织目录”。

两种模式共享同一套稳定身份、邮箱反查、冲突检测和审计规则。区别只在于是否主动创建所有外部成员，以及是否由来源维护组织节点和成员关系。

### 3.3 多供应商兼容原则

QM 从第一期开始采用“通用 Core + 能力驱动适配器”的结构：

- Core 只理解人员、身份、来源、供应商租户、外部 subject、组织单元和字段证据等通用概念。
- 企业微信是第一个供应商适配器，CorpID、UserID 和企业微信接口错误码只能出现在适配器边界内。
- 钉钉、飞书、Slack 等后续供应商通过新增适配器接入，不应修改 canonical 人员、身份唯一性、冲突处理和事务规则。
- 数据库、Core API 和 Admin API 不新增 `wecom_userid`、`wecom_department_id` 等供应商专用字段。
- Admin 根据来源声明的能力决定可用模式和操作，不能假设所有供应商都提供邮箱反查或部门树。
- 不把 Slack 频道、聊天群或其他协作容器默认映射为组织部门；只有供应商明确提供组织单元语义时才允许托管组织架构。

本 PRD 只要求实现企业微信适配器，不实现钉钉、飞书或 Slack。通用性通过 Core 契约、持久化命名、能力组合和适配器契约测试保证，不通过提前编写未使用的平台代码实现。

### 3.4 两种登录顺序

系统必须同时正确处理：

- 用户先用企业邮箱登录，之后再用企业微信扫码登录；
- 用户先用企业微信扫码登录并即时创建，之后再用企业邮箱登录。

无论顺序如何，最终都只能有一个 `organization_users`，其下同时关联企业邮箱身份和企业微信身份。

### 3.5 本期落地的失败关闭约束

- 自动邮箱关联和 JIT 必须同时满足 `verified_corporate_email` 策略、`trustedCorporateEmail` 能力和 `corporateEmailSubjectLookup` 能力；`manual_only` 或不可信邮箱来源不能绕过该门槛。
- 登录时临时观察到的外部 subject 不属于已对账成员快照。只有带有当前完整快照版本标记的成员才允许 JIT，重复扫码也不能把登录观察升级成快照成员。
- 邮箱反查熔断期间禁止 JIT 创建，空组织也不能让不具备可信邮箱反查能力的来源建立可创建用户的对账基线。
- 定向成员同步会使完整快照和邮箱对账基线失效；完成下一次完整同步前禁止 JIT 和托管组织预览。
- 托管提交绑定来源快照、组织授权版本和外部身份绑定指纹。预览后发生组织变更或身份重绑时必须重新预览。
- 来源进入暂停或删除状态后，所有通过该来源绑定的人员会话版本必须持久化递增；无论状态变化来自专用暂停接口、通用编辑接口、环境配置收敛还是其他实例，后台任务都必须幂等补偿，不能只依赖单个 HTTP 路由。
- 登录的最后一次来源状态校验、身份或人员事务，以及来源更新、暂停、删除和环境配置收敛必须使用同一来源级互斥。并发结果只能线性化为“登录先完成，随后状态变更并使该登录会话失效”或“状态变更先完成，登录失败关闭”，不能在最终校验后插入暂停或删除而留下有效会话。
- 企业邮箱可信度必须作为服务端签名断言中的显式布尔值传递。字段缺失等同于不可信，OIDC `email_verified` 不能根据邮箱字段是否存在来推断。

## 4. 产品目标

### 4.1 身份关联目标

- 对 QM 已知且已验证的企业邮箱，使用企业微信官方接口反查稳定 `userid`。
- 自动把邮箱身份和企业微信身份绑定到同一个组织成员。
- 支持企业微信扫码首次登录即时创建组织成员。
- 支持未绑定企业微信成员按需授权企业邮箱，并在创建前完成唯一匹配和冲突检查。
- 在并发登录、同步重试和多实例部署下保证不会重复创建人员。
- 对无法安全自动处理的冲突显式失败，并提供管理员处理入口。

### 4.2 组织目录目标

- 管理员可明确选择来源只参与登录，还是托管整个组织目录。
- 托管模式可同步部门树、人员、主部门和兼任部门。
- 外部目录只管理其拥有的字段和关系，不覆盖 QM 的访问组、权限、管理员角色和其他业务数据。
- 离职、移出可见范围和部门删除采用可审计、可恢复的停用或归档流程，不硬删除历史数据。

### 4.3 成功标准

- 邮箱先登录和企业微信先登录两条路径均只生成一个 canonical 人员。
- 已验证企业邮箱能够在无需管理员逐个操作的情况下自动关联企业微信身份。
- 企业微信第一次扫码没有返回邮箱时，未绑定用户进入按需手工授权；已绑定用户不受影响。
- 托管模式能准确反映外部部门树和成员关系，且不改变 ACL、访问组和管理员授权。
- 外部接口异常时，已绑定用户仍可登录；只有可能制造重复人员的新建路径被暂停。

## 5. 非目标

- 不把姓名、头像、手机号或推测邮箱作为单独的自动绑定依据。
- 不自动合并两个已经承载不同业务资源的 `organization_users`。
- 不允许多个外部来源同时成为同一组织的组织架构权威来源。
- 不让外部目录覆盖访问组、节点 manager、QM 管理员、权限管理者、项目、文件、会话、Skill 或 Cron。
- 不在浏览器端决定或传入可信的企业微信 `userid`。
- 不要求第一期支持所有目录供应商；接口抽象应通用，首个实现以企业微信为准。
- 不提前实现钉钉、飞书或 Slack 的接口、凭据页面和供应商专用数据转换。

## 6. 术语与不变量

### 6.1 Canonical 人员

`organization_users` 中的一条人员记录。所有登录身份、组织关系和业务资源最终都归属于其 `principal_id`。

### 6.2 外部主体

目录供应商返回的稳定成员标识。完整身份命名空间由供应商类型、供应商租户稳定 ID 和外部 subject 组成。企业微信外部主体为特定 CorpID 下的 `userid`；后续供应商使用各自适配器验证和规范化后的租户与成员稳定标识。

### 6.3 目录来源

管理员配置的一条供应商连接，包含凭据、模式、能力、同步状态和供应商租户引用。目录来源是运行连接，不等同于人员身份命名空间；轮换凭据或接管同一供应商租户时必须复用原来源和稳定身份映射。

### 6.4 已验证企业邮箱

由可信邮箱身份提供方完成所有权验证，且域名满足组织企业域名策略的邮箱。用户自行填写、管理员导入但未验证、企业微信个人邮箱字段均不能直接获得此资格。

### 6.5 反向身份解析

以已验证企业邮箱调用供应商接口，取得对应外部主体稳定 ID 的过程。企业微信使用 `email_type=1`，只解析企业邮箱。

### 6.6 必须始终成立的不变量

- 一个外部稳定身份在同一组织内最多绑定一个 `principal_id`。
- 一个邮箱身份的稳定 subject 在同一组织内最多绑定一个 `principal_id`。
- 一个组织成员可以绑定多个不同类型或不同来源的身份。
- 同一个供应商租户不能因凭据轮换、应用接管或来源恢复产生第二套身份命名空间。
- 自动流程只能补齐身份和允许托管的资料，不能移动既有业务资源到另一人员。
- 任意失败不得产生只写入一半的人员或身份关系。
- 登录、同步和反查结果必须持久化，不能仅依赖单进程内存。

## 7. 来源模式

### 7.1 仅登录与身份绑定

`identity_only` 模式具有以下行为：

- 同步外部成员快照，用于验证成员存在、状态和可见范围。
- 执行企业邮箱到外部主体的反向解析和已有成员自动绑定。
- 不因全量同步主动创建所有 `organization_users`。
- 不创建、重命名、移动或归档 QM 组织节点。
- 不主动维护 `org_unit_members`。
- 允许外部成员在满足即时创建安全门槛时，通过首次扫码只创建本人。

该模式适用于只希望使用企业微信登录，但继续在 QM 内维护成员和组织架构的客户。

### 7.2 托管组织目录

`managed_directory` 模式在上述能力基础上增加：

- 全量或增量同步外部部门树。
- 主动创建外部目录中的有效成员。
- 维护人员的主部门和兼任部门关系。
- 根据来源状态停用或归档来源拥有的人员和部门关系。
- 在提交变更前展示差异预览，并要求管理员确认首次启用或高风险变更。

每个 QM 组织同一时间最多有一个已启用的 `managed_directory` 来源。其他来源只能处于 `identity_only` 模式。

来源只有同时声明成员快照、组织单元和成员组织关系能力时，才可以选择 `managed_directory`。能力不足时 Admin 必须禁用该选项并说明缺少的能力，而不是以空部门树降级执行。

### 7.3 模式切换

从 `identity_only` 切换到 `managed_directory`：

1. 校验该组织不存在另一个托管来源。
2. 完成部门和成员全量预览。
3. 展示预计新增、更新、停用、归档和冲突数量。
4. 管理员明确确认后才开始写入。

从 `managed_directory` 切换到 `identity_only`：

- 立即停止外部来源对组织节点、人员资料和成员关系的后续写入。
- 保留已经导入的人员、组织节点、绑定和历史关系，不批量删除或移动。
- 外部登录和身份关联按 `identity_only` 继续工作。
- 在 Admin 中提示组织架构已转为 QM 手工维护。

## 8. 企业微信接口策略

### 8.1 成员同步

同步仍以企业微信稳定 `userid`、部门 ID、成员状态和应用可见范围为基础。若接口合法返回 `biz_mail`，可将其作为企业微信验证过的企业邮箱资料，但系统不能假设该字段始终可用。

`email` 个人邮箱字段不参与企业邮箱自动绑定。

### 8.2 扫码登录的按需手工授权

企业微信 Web 扫码接口只作为稳定身份发现步骤。Core 使用扫码回调换取同一 CorpID 下的 `userid`，不能假设该接口或普通成员详情接口会返回邮箱。

扫码后的处理顺序固定为：

1. 生成只包含来源、CorpID、UserID 和当前可用资料的短期签名断言。
2. 按供应商租户和外部 subject 查询持久化身份绑定。
3. 已绑定时直接登录 canonical 人员，不索要额外资料授权，也不依赖邮箱。
4. 未绑定且断言没有可信 `biz_mail` 时，将签名续接请求写入 Core 的持久化一次性事务，向企业微信只发送 64 位十六进制随机 `state`，再发起 `snsapi_privateinfo` 手工授权。
5. Core 使用授权码调用“获取访问用户身份”取得 `user_ticket`，再调用“获取访问用户敏感信息”取得用户授权的资料。
6. 两次回调取得的 `userid`、敏感信息返回的 `userid`、来源 CorpID 和 Provider 必须完全一致；任何不一致、取消、过期或接口失败都失败关闭。
7. 只有 `biz_mail` 进入企业邮箱唯一匹配和即时创建；`email` 仍作为个人邮箱资料，不获得自动绑定资格。

企业微信收到的 `state` 只包含随机值，满足最多 128 字节且仅含字母数字的接口约束；完整 OIDC 请求、Provider、租户和预期 UserID 留在持久化事务中，并在第二次回调时原子领取。`user_ticket` 只在 Core 的单次服务端调用中使用，不进入浏览器状态、OIDC 令牌、日志或持久化存储。第二段授权完成后生成新的短期目录登录断言，第一段没有邮箱的断言不能直接用于未绑定用户的创建。

Core 与 Auth 的首次扫码解析使用显式协议版本。需要敏感资料授权时 Core 返回非成功的前置条件状态；旧 Auth 因而失败关闭。新 Auth 拒绝缺少协议版本的旧 Core 响应，避免蓝绿发布期间把“未知”解释为“不需要授权”。官方接口依据：

- [企业微信：Web 登录组件获取登录用户信息](https://developer.work.weixin.qq.com/document/path/98176)
- [企业微信：构造网页授权链接](https://developer.work.weixin.qq.com/document/path/91022)
- [企业微信：获取访问用户身份](https://developer.work.weixin.qq.com/document/path/91023)
- [企业微信：获取访问用户敏感信息](https://developer.work.weixin.qq.com/document/path/95833)

### 8.3 企业邮箱反查

对满足条件的邮箱调用：

`POST /cgi-bin/user/get_userid_by_email?access_token=...`

请求使用 `email_type=1`。成功返回的 `userid` 只有在以下条件同时满足时才可作为自动绑定依据：

- 邮箱来自已验证邮箱身份或其他明确标记为可信的企业邮箱来源；
- 邮箱域名在组织允许的企业域名中；
- `userid` 存在于同一来源的有效成员快照中；
- 来源 CorpID 与当前登录或同步上下文一致；
- 该外部身份没有绑定到另一个 canonical 人员；
- 反查结果没有过期，且对应来源快照版本仍有效。

### 8.4 调用控制

由于供应商会对错误邮箱比例和调用频率进行限制，系统必须：

- 只反查新增或发生变化的已验证企业邮箱；
- 持久化成功、未找到、限流和临时错误结果；
- 对未找到和临时错误使用不同退避时间；
- 设置每来源调用速率、并发上限和每日错误预算；
- 达到错误预算或明确限流后持久化打开熔断器；
- 熔断期间不继续试探大量邮箱，只按退避计划做少量恢复探测；
- 在 Admin 中显示暂停原因和预计重试时间，但不暴露凭据或供应商原始敏感响应。

不得在每次页面加载、每次目录全量同步或每次已绑定用户登录时重复反查不变邮箱。

## 9. 邮箱先登录流程

### 9.1 前置条件

- 邮箱身份提供方已经验证邮箱所有权。
- 邮箱满足组织准入策略。
- 组织存在可用于该域名的企业微信来源，且来源允许登录。

### 9.2 处理顺序

1. 按邮箱身份的稳定 subject 查找现有身份绑定。
2. 若已绑定，直接解析到现有 `principal_id`，并异步刷新过期的企业微信反查结果。
3. 若未绑定，使用规范化后的已验证企业邮箱读取有效反查缓存；缓存不存在或过期时调用企业微信邮箱反查接口。
4. 取得 `userid` 后，确认该企业微信稳定身份是否已经绑定。
5. 若企业微信身份已绑定，将邮箱身份追加到同一个 `principal_id`，并在字段归属允许时补全 `organization_users.email`。
6. 若企业微信身份未绑定，但存在邮箱对应的唯一组织成员，将企业微信身份和邮箱身份都绑定到该成员。
7. 若两类身份都未绑定且组织准入策略允许创建，则创建一个成员，并在同一事务中绑定两类身份。
8. 若反查未找到或服务不可用，不得猜测 `userid` 或绑定到同名人员。

### 9.3 反查失败时的准入

- 已有邮箱身份绑定：不影响登录。
- 已有唯一邮箱成员但尚无邮箱身份：可以只完成邮箱身份绑定和登录，不创建第二个人员；企业微信关联保持待解析。
- 完全未知的邮箱主体：沿用组织现有邮箱准入策略决定是否允许创建。如果该组织已启用企业微信即时创建，为避免与稍后扫码产生重复人员，默认暂缓自动创建并提示稍后重试或联系管理员。
- 管理员可为特定来源关闭上述防重复门槛，但 Admin 必须展示可能产生重复人员的风险；第一期默认不提供此例外开关。

## 10. 企业微信先登录流程

### 10.1 已绑定身份

扫码登录代理验证企业微信回调后，服务端生成签名登录断言。Core 按“Provider + CorpID + UserID”查找绑定；已绑定时直接登录对应成员，不依赖当次接口是否返回邮箱，也不发起 `snsapi_privateinfo`。

### 10.2 未绑定身份即时创建

Core 确认不存在稳定绑定后，若第一次扫码断言没有可信 `biz_mail`，必须先完成 8.2 的手工授权。授权后的 UserID 必须与扫码 UserID 一致，企业邮箱才能进入下述匹配和创建流程。用户拒绝授权、授权未返回 `biz_mail` 或身份一致性校验失败时，不得猜测邮箱、创建无邮箱人员或绑定到同名人员。

未绑定的企业微信成员只有同时满足以下条件才可即时创建：

- 来源处于启用状态，并允许该应用发起登录；
- `userid` 位于该来源当前有效的成员快照中；
- 外部成员状态允许登录；
- 来源已完成身份对账基线，且对账新鲜度未超过配置阈值；
- 来源反查服务和持久化熔断状态允许创建；
- 没有同一稳定身份的冲突绑定；
- 组织准入策略允许由该来源即时创建。

创建行为：

1. 使用当次手工授权取得的可信 `biz_mail`，并与成员快照中存在的可信企业邮箱证据做一致性检查。
2. 若能唯一解析到现有人员，只追加企业微信身份，不创建人员。
3. 若不能解析且无冲突，创建 `organization_users`。
4. 将可信企业邮箱写入新人员；缺失企业邮箱时失败关闭。
5. 在同一事务中创建企业微信身份绑定、成员状态和审计记录。

### 10.3 后续邮箱登录

用户之后使用企业邮箱登录时，系统以已验证企业邮箱反查 `userid`：

- 如果返回的企业微信身份已经绑定到扫码创建的成员，将邮箱身份追加到该成员；
- 如果该成员的邮箱为空，按字段归属规则补全；
- 如果返回的企业微信身份和邮箱身份分别指向不同成员，进入冲突状态，不自动合并；
- 完成后，任一登录方式都解析到同一 `principal_id`。

## 11. 身份对账与即时创建安全门槛

### 11.1 对账基线

新来源首次启用企业微信即时创建前，系统必须对组织中所有符合企业域名条件且已验证的邮箱执行一次受控反查，生成基线：

- 已解析并自动绑定；
- 已解析但发生冲突；
- 供应商未找到；
- 因限流或错误尚未完成；
- 不符合反查条件。

只有当待处理和临时错误降至零、冲突已被管理员确认处理、基线对应当前来源配置和成员快照时，才能启用未绑定企业微信用户的即时创建。

### 11.2 新鲜度

对账基线必须记录来源配置指纹、成员快照版本和完成时间。以下变化使基线失效：

- CorpID、凭据、应用可见范围或企业域名变化；
- 来源被删除、恢复、暂停或重新启用；
- 供应商返回表明权限范围发生变化；
- 成员快照超过允许的新鲜度；
- 管理员切换来源模式。

基线失效时：

- 已绑定身份继续登录；
- 不创建新的企业微信扫码成员；
- 后台重新执行增量对账；
- Admin 明确显示阻塞原因和恢复进度。

来源暂停、删除、恢复或重新启用必须立即清除旧基线和 JIT 资格。完整同步得到完全相同的组合快照版本时可保留现有基线；快照发生变化时必须标记基线失效、关闭 JIT，并自动排队重新对账，不能依赖管理员手工触发。

### 11.3 增量对账

以下事件触发单邮箱或小批量增量对账：

- 新的已验证企业邮箱身份首次出现；
- 成员企业邮箱发生变更；
- 外部成员首次出现在同步快照中；
- 管理员解决冲突或手工修正绑定；
- 负缓存到期；
- 熔断恢复。

## 12. 托管组织目录同步

### 12.1 同步对象

托管模式同步：

- 部门稳定 ID、名称、父部门 ID、排序和有效状态；
- 成员稳定 ID、显示名称、职位及供应商实际可见且允许托管的资料；
- 成员主部门；
- 成员兼任部门；
- 成员在来源中的在职、停用或离开状态。

成员详情接口中的部门字段不足以构建完整部门树。企业微信适配器应优先使用“获取子部门 ID 列表”取得稳定父子关系，再用“获取单个部门详情”补充名称等资料。普通自建应用只能读取应用可见范围内的部门，接口未返回部门名称时不能以 ID 伪装为真实名称后静默托管；系统必须将其作为能力不足或资料不完整展示在预览中。

### 12.2 组织节点映射

- 外部部门以“来源 ID + 外部部门稳定 ID”映射到 QM 组织节点。
- 节点名称只用于展示和变更，不作为主键。
- 不因同名而自动复用手工创建的 QM 节点。
- 首次导入遇到疑似同名节点时，在预览中提示管理员选择“新建来源节点”或显式映射。
- 上述选择持久化为带来源 revision 栅栏的节点映射；选择变化后，之前生成的预览立即失效，必须重新预览。
- 显式映射到手工节点后，来源只维护外部部门到该节点的关系，不取得该节点的名称、父节点、排序或生命周期所有权。
- 来源创建的节点必须记录来源所有权。
- 外部部门改名或移动时，更新已映射节点，不创建重复节点。

### 12.3 人员创建与资料归属

托管模式会为来源中的有效成员主动创建 canonical 人员，但创建前必须依次检查稳定身份绑定、可信邮箱反查和现有唯一邮箱成员。

字段归属遵循以下规则：

| 数据                | 托管来源权限 | 规则                                               |
| ------------------- | ------------ | -------------------------------------------------- |
| 企业微信稳定身份    | 管理         | 以稳定 ID 创建和维护绑定                           |
| 显示名称、职位      | 可管理       | 仅在供应商返回明确值时更新                         |
| 企业邮箱            | 可补全       | 只接受可信 `biz_mail` 或已验证邮箱，不以缺失值清空 |
| 主部门、兼任部门    | 管理         | 仅维护映射到来源节点的关系                         |
| 用户状态            | 可管理       | 按离职和停用规则变更，不硬删除                     |
| 访问组              | 不管理       | 保留 QM 状态                                       |
| 节点 manager        | 不管理       | 保留 QM 状态                                       |
| QM 管理员和权限角色 | 不管理       | 保留 QM 状态                                       |
| 业务资源            | 不管理       | 文件、项目、会话、Skill、Cron 等均不改变           |

供应商字段缺失表示“本次不可见或未提供”，不等于清空。只有供应商明确发送空值、字段属于来源管理且接口语义能区分“空值”与“缺失”时，系统才可清空。

### 12.4 部门关系

- 一个成员最多有一个主部门，可有多个兼任部门。
- 外部主部门映射为 QM 主组织节点关系。
- 其他部门映射为兼任关系。
- 来源只删除自己创建或拥有的成员关系，不删除管理员手工添加且未归属该来源的关系。
- 外部成员暂时缺少部门信息时保留上次有效关系，并将记录标记为待确认，避免权限或目录瞬间大面积漂移。

### 12.5 离职、不可见与删除

以下情况必须区分：

- 明确离职或被供应商停用：立即禁止通过该来源新建会话，并按策略暂停组织成员。
- 暂时移出应用可见范围：标记来源不可见，进入宽限期，不立即停用 canonical 人员。
- 单次同步未返回：视为不完整同步风险，不做破坏性变更。
- 来源部门删除：先归档来源节点；有手工关系、子节点或业务引用时不得硬删除。

本期实现采用连续两次完整同步缺失确认：首次缺失只记录待确认状态，不暂停人员或归档部门；第二次完整同步仍缺失时才进入非活跃计划。已有活跃数据时，空成员快照或空部门快照直接拒绝提交。供应商明确返回的离职或停用状态不受缺失确认次数影响。

默认宽限期由产品配置给出，并在首次启用托管模式的预览中展示。宽限期结束后的状态变化必须进入审计记录。恢复可见后应复用原人员、节点和稳定映射。

## 13. 冲突与失败处理

### 13.1 身份冲突

下列情况禁止自动合并：

- 已验证邮箱身份指向人员 A，反查得到的企业微信身份已绑定人员 B；
- 同一个企业微信稳定身份出现两个人员绑定候选；
- 同一个邮箱 subject 已绑定多个人员；
- 反查 `userid` 不在当前来源有效成员快照中；
- 目标人员已被删除、永久停用或属于另一个组织；
- 远端反查完成后，来源配置或成员快照版本发生变化。

系统必须记录结构化冲突，阻止产生新的重复人员，并让管理员在匹配工作台中处理。管理员可以选择正确人员并解除错误绑定，但不能在该工作台直接自动迁移两个成员的业务资源。

### 13.2 已存在重复人员

如果历史数据已经分别创建邮箱人员和企业微信人员：

- 系统检测并展示冲突，不静默选择任意一方；
- 两个人员均保留，避免业务资源丢失；
- 管理员先选择保留的 canonical 人员；
- 资源迁移和人员合并属于独立的受审计能力，不纳入本 PRD；
- 完成合并能力前，管理员只能纠正身份绑定，并自行处理相关业务归属。

### 13.3 外部服务异常

- 已绑定身份的登录不依赖实时反查，继续可用。
- 新的企业微信即时创建在对账服务不可用、基线过期或熔断时失败关闭。
- 已存在邮箱人员的邮箱登录不受企业微信反查故障影响；企业微信关联可延后完成。
- 同步保留上次成功快照，不以空结果覆盖。
- 管理员手工绑定仍需通过稳定身份唯一性检查。

### 13.4 用户提示

登录端使用不泄露组织成员信息的通用提示，例如“暂时无法完成身份关联，请稍后重试或联系管理员”。Admin 可查看结构化原因、来源、时间、重试状态和建议动作，但不显示敏感令牌或完整供应商响应。

## 14. 数据与持久化要求

### 14.1 `directory_sources`

增加或等价表达以下配置：

- `mode`：`identity_only | managed_directory`；
- `provider_type`：供应商适配器类型；
- `provider_tenant_id`：适配器验证并规范化的企业、租户或工作区稳定 ID；
- `capabilities`：适配器探测并由服务端确认的能力集合；
- `jit_provisioning_enabled`：是否允许受控即时创建；
- `reconciliation_status`：未开始、运行中、就绪、阻塞、失效；
- `reconciled_source_revision`：完成基线时的来源版本；
- `reconciled_at`：基线完成时间；
- `reconciliation_expires_at`：基线失效时间；
- `managed_directory_confirmed_at`：托管预览确认时间。

模式、CorpID、凭据、企业域名、可见范围或关键能力变化必须生成新的来源配置版本，并使旧对账基线失效。

Core 的持久化模型使用 `provider_type`、`provider_tenant_id`、`external_subject_id` 和 `external_unit_id` 等通用名称。供应商原始字段只保存在适配器自己的凭据或快照载荷边界内，不成为跨供应商业务逻辑的查询条件。

### 14.2 身份绑定

系统只能有一个决定 canonical `principal_id` 的权威身份绑定服务。现有 `auth_identities` 与 `external_identity_bindings` 应在技术设计中收敛为单一写入入口；无论底层最终使用一张表还是协议投影，都必须具备：

- 组织 ID；
- 身份类型和签发方；
- 稳定 subject；
- 来源 ID；
- canonical `principal_id`；
- 绑定方式：登录、邮箱反查、同步、管理员；
- 绑定时邮箱快照或其安全审计引用；
- 创建、更新和撤销时间。

数据库唯一约束必须覆盖“组织 + 签发方 + 稳定 subject”，不能只依赖应用层检查。

外部目录身份还必须对“组织 + 供应商类型 + 供应商租户 ID + 外部 subject”建立唯一约束。`directory_source_id` 可作为证据来源和运行连接引用，但不能让同一供应商租户仅因更换连接记录而重复创建身份。

### 14.3 邮箱反查结果

新增持久化的企业邮箱解析记录，至少包含：

- 组织 ID、来源 ID；
- 对应的邮箱主体或组织成员引用；
- 用于判断变化的规范化邮箱摘要；
- 解析状态：`resolved | not_found | conflict | temporary_error | rate_limited`；
- 解析出的外部 subject；
- 来源配置版本和成员快照版本；
- 最近检查时间、下次重试时间和失败计数；
- 供应商错误的安全分类，不保存不必要的原始响应。

若邮箱已存在于组织成员或身份资料中，不应在额外表重复保存更多明文副本。摘要必须采用带服务端密钥的不可逆计算，不能用可枚举的裸哈希。

### 14.4 部门快照与映射

托管模式需要持久化：

- 外部部门快照：稳定 ID、父 ID、名称、排序、状态、来源版本；
- 外部部门到 QM 组织节点的映射；
- 节点和成员关系的来源所有权；
- 最后一次确认存在时间、宽限期和归档状态。

来源所有权必须精确到关系，不能只在节点或人员级别做一个笼统标记，否则无法区分来源同步关系与管理员手工关系。

管理员的“创建新节点”或“映射现有节点”决策必须绑定到一个未过期的持久化预览。服务端需重新校验预览中的来源版本、成员快照版本、组织版本、身份指纹、同名冲突候选和目标节点父级；客户端不能提交任意目标节点 ID。映射写入和对应审计事件必须在同一个来源存储事务中提交，任一步失败都不能留下无审计映射。

### 14.5 同步运行与预览

同步运行、预览差异、提交结果、失败明细、进度和重试状态必须持久化到 Postgres。多实例切换或部署重启后，Admin 仍能读取同一任务状态，不能依赖进程内 `Map` 或内存队列作为权威记录。

托管提交开始后，预览进入持久化 `committing` 状态。来源锁覆盖最终校验、人员创建、组织事务、所有权写入和身份状态投影；各步骤使用稳定系统执行者、确定性节点 ID、关系所有权及会话版本实现幂等重放。同一来源存在未完成的 `committing` 预览时，不能创建或提交另一份托管预览，避免旧恢复任务覆盖较新的托管结果。组织变更与提交结果标记必须写在同一个组织事务内：恢复任务只有读到该标记时才允许跳过预览版本校验并继续所有权与身份状态投影；没有标记时仍须重新校验来源、映射、组织版本和身份指纹。进程中断后由周期性后台恢复任务反复使用同一个预览继续收敛，不能只在启动时尝试一次，也不能把已由来源暂停的账号误判为管理员手工暂停。成员读取必须完整遍历持久化快照游标并检测游标循环，任何页面上限都不能静默截断托管预览。密钥表等 schema 扩展必须兼容蓝绿部署中的旧 writer 和回滚，不得在同一次迁移中立即增加旧二进制无法满足的非空写入约束。

## 15. 服务与适配器契约

### 15.1 供应商能力

通用目录适配器应声明能力，而不是在 Core 中硬编码企业微信分支。至少包括：

- `memberSnapshot`：读取外部成员稳定身份和状态；
- `corporateEmailSubjectLookup`：用已验证企业邮箱解析外部 subject；
- `organizationUnits`：读取部门树；
- `memberOrganizationUnits`：读取主部门和兼任部门；
- `trustedCorporateEmail`：供应商是否可能直接返回可信企业邮箱。
- `incrementalSync`：供应商是否支持游标、事件或其他增量变化读取。
- `deprovisioning`：供应商是否能区分停用、离职与暂时不可见。

不支持某能力的供应商必须返回明确的“不支持”，不能返回空数据让 Core 误判为删除。

能力名称及输入输出由通用契约定义。供应商适配器可以返回供应商专用的安全错误分类，但 Core 只能基于统一的成功、未找到、无权限、限流、临时错误和不支持等结果执行策略。

### 15.2 登录断言

企业微信回调由服务端验证后生成签名断言。断言至少包含：

- 组织和来源 ID；
- 供应商租户标识；
- 外部稳定 subject；
- 登录时间、过期时间和防重放标识；
- 当次供应商实际返回且已分类可信度的资料。
- 企业邮箱可信度的显式布尔值；缺失时按 `false` 处理。

浏览器提交的 `userid`、邮箱、CorpID 或来源 ID 不能覆盖服务端断言内容。

### 15.3 Core 身份解析入口

邮箱登录、企业微信登录、后台对账和托管同步必须调用同一个身份解析与绑定服务。该服务负责唯一性检查、字段归属、事务写入、冲突记录和审计，避免四条路径各自实现不同规则。

### 15.4 适配器边界

每个供应商适配器负责：

- 验证供应商租户和登录回调；
- 将供应商成员稳定 ID 规范化为 `external_subject_id`；
- 将部门或团队稳定 ID 规范化为 `external_unit_id`；
- 把供应商状态、邮箱证据和组织关系转换为通用快照；
- 声明并探测当前凭据实际可用的能力；
- 将供应商错误转换为通用、安全的错误分类。

Core 负责：

- canonical 人员创建和状态变更；
- 多身份绑定、匹配顺序和冲突检测；
- 来源模式、字段归属和组织目录写入；
- 反查调度、持久化退避、熔断和新鲜度；
- 事务、并发、审计、指标和管理员授权。

适配器不得直接写入 `organization_users`、身份绑定、组织节点或成员关系。Core 不得根据 `provider_type` 分支调用供应商 URL 或解析供应商原始响应。

### 15.5 第一阶段能力矩阵

| 能力         | 企业微信                 | 其他供应商         |
| ------------ | ------------------------ | ------------------ |
| 登录         | 本期实现                 | 不实现，仅保留契约 |
| 成员快照     | 本期实现                 | 不实现，仅保留契约 |
| 企业邮箱反查 | 本期实现                 | 可选能力，不实现   |
| 可信企业邮箱 | 按实际授权返回           | 可选能力，不实现   |
| 组织单元     | 托管模式本期实现         | 可选能力，不实现   |
| 成员组织关系 | 托管模式本期实现         | 可选能力，不实现   |
| 增量同步     | 按企业微信能力决定       | 可选能力，不实现   |
| 离职与停用   | 按企业微信可验证状态实现 | 可选能力，不实现   |

## 16. 并发与事务

### 16.1 远端调用边界

企业微信反查不能放在长数据库事务中。推荐流程：

1. 读取来源版本和候选状态。
2. 调用远端接口或读取有效缓存。
3. 获得带来源版本、成员快照版本和检查时间的解析证据。
4. 获取来源级或稳定身份级的分布式互斥。
5. 开启数据库事务并重新读取关键状态。
6. 确认版本未变化、成员仍有效、唯一约束仍成立。
7. 原子写入人员、身份、资料、冲突或审计。

### 16.2 并发首次登录

邮箱登录和企业微信扫码可能同时发生。系统必须依靠数据库唯一约束、稳定的锁键和可重试事务保证：

- 最多创建一个 `organization_users`；
- 两个身份最终绑定同一个 `principal_id`；
- 唯一约束竞争的失败方重新读取结果并复用胜出记录；
- 重试不会重复写审计或重复创建关系。

来源级互斥还必须覆盖已绑定登录和 JIT 登录的最终组织事务，并与来源更新、暂停、删除使用同一锁键。PostgreSQL 实现使用跨实例 advisory lock；内存实现只用于测试和单进程开发，但必须保持相同的可重入语义。来源状态写入必须在取得该锁后重新读取 revision，不能只依赖进入锁前的快照。

当登录与暂停或删除并发时，允许的结果只有两种：登录先提交后由状态变更递增相关人员的持久化会话版本，或状态变更先提交后登录因来源不可用而拒绝。两者都不能产生暂停来源下仍有效的新会话或遗漏新建绑定的会话失效。

### 16.3 同步并发

同一来源不能同时提交两个写入型同步运行。预览可以与同步并行读取，但提交时必须验证其基于的来源版本和快照版本仍然有效。过期预览必须重新生成，不能继续提交。

## 17. Admin Web 需求

### 17.1 新增来源向导

在身份来源配置中增加“同步模式”：

- “仅登录与身份绑定”：说明不会批量创建人员或修改组织架构，首次扫码可按安全规则创建本人。
- “托管组织目录”：说明将创建和维护部门、人员及部门关系，但不会管理权限和访问组。

选择托管模式后，向导必须展示：

- 当前组织是否已有托管来源；
- 将由来源管理的字段；
- 不会被覆盖的数据；
- 离职和不可见成员处理策略；
- 预览入口和确认要求。

### 17.2 来源详情

来源详情至少展示：

- 当前模式和登录状态；
- 凭据与连接测试状态；
- 最近成功成员同步和部门同步时间；
- 身份对账状态、新鲜度和来源版本；
- 已解析、未找到、冲突、待重试数量；
- 即时创建是否可用及阻塞原因；
- 反查限流、错误预算和熔断状态；
- 托管目录最近一次预览和提交结果。

### 17.3 对账工作台

在现有匹配工作台基础上增加：

- 按邮箱先登录、企业微信先登录、批量同步分类查看来源；
- 查看系统为何将两个身份解析为同一人员；
- 查看冲突两侧的稳定身份、当前绑定和资料差异；
- 重试单条反查；
- 选择正确的 canonical 人员并修正绑定；
- 对未找到结果保持忽略或重新启用自动解析；
- 所有操作要求二次确认并记录操作者。

### 17.4 托管预览

预览必须分组显示：

- 新增、改名、移动、归档的组织节点；
- 新增、更新、暂停的人员；
- 新增、变更、移除的主部门和兼任部门关系；
- 自动绑定、待处理和冲突身份；
- 因字段缺失而保持不变的数据；
- 预计不受影响的访问组、权限和管理员角色。

关系差异必须逐项标明新增、主次变更、移除、不变或保留；手工节点、手工关系及因来源字段缺失而保留的人员资料必须单列。待归档节点还必须展示活跃子节点、成员、目录可见范围根和 ACL 引用数量，不能只显示节点数量汇总。

预览只读，不得产生人员、节点、关系或身份绑定。提交按钮仅对仍匹配当前来源版本的预览可用。

Admin 除汇总数量外，必须展示变更节点和人员明细、来源快照版本、组织版本、过期时间和冲突；完整预览应可下载。任何类型的 ACL、目录可见范围、负责人或其他授权引用都会阻止相关组织节点归档，界面不得声称未检查的授权一定会被保留。

## 18. 权限、安全与隐私

- 只有组织管理员可以新增来源、切换模式、确认托管预览、处理身份冲突或删除来源。
- 凭据加密保存，只写不回显；环境管理凭据沿用现有只读规则。
- 企业邮箱、姓名和外部 subject 不进入指标标签。
- 普通日志不记录完整邮箱、access token、原始回调或供应商响应。
- 反查接口的错误详情仅以安全分类持久化。
- 登录断言必须签名、短时有效、防重放，并绑定预期来源和组织。
- 管理员手工绑定不能绕过组织边界、稳定身份唯一性和成员状态检查。
- 暂停或删除来源后，通过该来源建立的新会话按现有安全策略失效；历史身份和审计记录保留。

## 19. 审计与指标

### 19.1 审计事件

至少记录：

- 来源模式变更和托管预览确认；
- 对账基线开始、完成、失效和阻塞；
- 邮箱反查成功、未找到、限流和熔断状态变化；
- 即时创建人员；
- 邮箱身份与企业微信身份自动关联；
- 管理员修正绑定；
- 身份冲突创建和解决；
- 来源创建、更新、暂停、恢复和删除组织节点或成员关系；
- 成员因外部状态被暂停或恢复。

审计事件应引用内部记录 ID，展示层按权限解析必要资料，避免把 PII 复制到不可控日志。

### 19.2 指标

至少提供：

- 企业邮箱反查请求数、成功率、未找到率、限流率和延迟；
- 每来源对账完成度和新鲜度；
- 自动双身份关联数；
- 企业微信即时创建数；
- 因安全门槛阻止的即时创建数；
- 身份冲突数和解决耗时；
- 托管同步新增、更新、暂停和归档数；
- 同步失败率、熔断状态和恢复时间。

指标只使用组织、来源、结果分类等低基数字段，不包含邮箱、姓名、`userid` 或 `principal_id`。

## 20. 上线与迁移

### 20.1 阶段 A：反查能力与只读对账

- 增加通用企业邮箱反查能力和企业微信实现。
- 只生成持久化对账结果和 Admin 预览，不改变身份绑定。
- 验证供应商权限、错误预算、负缓存和熔断策略。

### 20.2 阶段 B：已有人员自动绑定

- 对无冲突的唯一结果自动绑定企业微信身份。
- 保持未知企业微信登录失败关闭。
- 处理现有手工绑定和历史重复人员冲突。

### 20.3 阶段 C：仅登录模式即时创建

- 已有来源默认迁移为 `identity_only`，不自动开启即时创建。
- 完成对账基线后，由管理员明确启用企业微信即时创建。
- 灰度验证邮箱先登录、企业微信先登录和并发首次登录。

### 20.4 阶段 D：托管组织目录预览

- 同步部门快照和映射，但仅生成只读差异。
- 验证字段归属、同名节点、离职、不可见和不完整同步场景。
- 现有来源不会因版本升级自动进入托管模式。

### 20.5 阶段 E：托管写入

- 管理员确认预览后启用来源拥有的组织节点、人员和关系写入。
- 首批运行按组织灰度，并保留暂停和恢复能力。
- 观察冲突、归档和权限不变性指标后再扩大范围。

### 20.6 兼容策略

- 现有来源在迁移后保持“仅登录与身份绑定”和即时创建关闭，确保行为不突变。
- 现有稳定身份绑定原样保留，不因增加反查记录重新分配人员。
- 现有管理员手工绑定优先于新自动候选；发现矛盾时生成冲突，不覆盖。
- 已有组织节点和成员关系默认视为 QM 手工数据，除非管理员在托管预览中显式映射给来源。

## 21. 验收标准

### 21.1 企业邮箱反查

- [ ] 只对已验证且属于允许企业域名的邮箱使用 `email_type=1` 反查。
- [ ] 成功结果必须同时通过来源、CorpID、成员快照和唯一性校验。
- [ ] 不变邮箱命中持久化缓存，不重复调用供应商。
- [ ] 未找到、限流和临时错误分别退避，并能在重启后延续。
- [ ] 超过错误预算后熔断，Admin 可见原因和恢复状态。

### 21.2 邮箱先登录

- [ ] 邮箱用户先创建后，反查得到未绑定 `userid` 时自动追加企业微信身份。
- [ ] 用户之后扫码登录解析到原 `principal_id`，不创建第二个人员。
- [ ] 若企业微信身份已属于另一人员，生成冲突且不自动合并。
- [ ] 反查不可用时，已有邮箱身份仍可登录。

### 21.3 企业微信先登录

- [ ] 已绑定成员第一次扫码取得 UserID 后直接登录，不发起敏感资料授权。
- [ ] 未绑定有效成员只有在 `snsapi_privateinfo` 返回相同 UserID 和可信 `biz_mail` 后才能匹配或创建。
- [ ] 已有唯一企业邮箱人员时只追加企业微信身份，不创建第二个人员。
- [ ] 用户拒绝授权、未返回 `biz_mail` 或两段 UserID 不一致时失败关闭。
- [ ] 不根据 `userid` 或姓名推测邮箱。
- [ ] 基线失效、成员无效或熔断时，不创建新人员。
- [ ] 已绑定企业微信身份在反查服务异常时仍可登录。

### 21.4 并发和原子性

- [ ] 邮箱首次登录与企业微信首次扫码并发时只创建一个人员。
- [ ] 任意事务失败不会留下孤立人员、孤立身份或半写入关系。
- [ ] 唯一约束竞争能够重读并复用胜出记录。
- [ ] 多实例重启不丢失对账、熔断、同步或预览状态。

### 21.5 仅登录与身份绑定

- [ ] 全量同步不批量创建人员，不修改组织节点和部门关系。
- [ ] 满足门槛的扫码登录只即时创建当前用户。
- [ ] 模式页面清楚说明该来源不会托管组织架构。

### 21.6 托管组织目录

- [ ] 每个组织最多启用一个托管来源。
- [ ] 部门改名和移动复用稳定映射，不创建重复节点。
- [ ] 主部门和兼任部门关系准确同步。
- [ ] 来源缺失字段不清空 QM 已有资料。
- [ ] 访问组、ACL、节点 manager、QM 管理员和业务资源保持不变。
- [ ] 节点归档影响同时检查 ACL 的 owner、grantee 和 Skill 访问策略的 owner 引用，任一引用存在都阻止归档。
- [ ] 单次空结果或不完整同步不会大面积停用人员或归档节点。
- [ ] 离职、不可见和删除按不同策略处理，并可恢复和审计。
- [ ] 从托管模式切回仅登录模式后停止写入，但保留已导入状态。

### 21.7 Admin 与安全

- [ ] 首次启用托管模式前必须查看并确认仍然有效的差异预览。
- [ ] 预览操作本身不写入人员、身份、节点或关系。
- [ ] 冲突工作台能够解释证据并支持管理员纠正绑定。
- [ ] 浏览器不能伪造或覆盖服务端验证的外部稳定身份。
- [ ] 来源暂停或删除后，既有会话在所有状态变更入口和多实例后台收敛路径中失效，重复执行不会重复递增会话版本。
- [ ] 登录代理只按签名断言中的显式可信标记生成 `email_verified`，不因邮箱存在而推断。
- [ ] 日志和指标不包含完整邮箱、令牌或外部成员 PII。

### 21.8 多供应商通用性

- [ ] Core 身份与组织目录服务不引用企业微信专用字段、URL 或错误码。
- [ ] 企业微信功能通过通用供应商适配器注册和能力声明接入。
- [ ] 使用假的契约测试适配器可验证“仅登录”“成员但无部门”“完整托管目录”等不同能力组合。
- [ ] 缺少组织单元能力的来源无法选择 `managed_directory`。
- [ ] 同一 canonical 人员可以绑定来自多个供应商租户的身份。
- [ ] 同一供应商租户轮换凭据或接管来源后复用原身份命名空间。
- [ ] 未实现的钉钉、飞书和 Slack 不产生运行时代码路径、配置项或数据库专用字段。

## 22. 测试场景

实现阶段至少覆盖以下自动化和端到端场景：

1. 已有邮箱人员，反查成功，后续企业微信扫码复用同一人员。
2. 未绑定企业微信成员第一次扫码无邮箱，手工授权后按 `biz_mail` 复用或创建人员。
3. 企业微信直接返回可信 `biz_mail`，首次扫码复用已有邮箱人员。
4. 两种首次登录并发，数据库最终只有一个人员和两条身份。
5. 邮箱人员与企业微信身份已分别绑定不同人员，系统只生成冲突。
6. 反查未找到、错误率超限、供应商限流、凭据过期和熔断恢复。
7. 来源快照在远端调用后发生变化，事务拒绝过期证据并重试。
8. 已绑定成员在供应商异常时继续登录，未知成员即时创建被阻止。
9. 托管模式首次导入部门树、成员、主部门和兼任部门。
10. 外部部门改名、移动、删除和恢复，稳定映射保持不变。
11. 成员离职、临时不可见、单次同步缺失和重新出现。
12. 外部字段缺失时保留 QM 资料，明确空值仅按字段归属清空。
13. 托管同步前后访问组、权限、管理员角色和业务资源完全不变。
14. 切换两种模式，确认写入边界和已有数据保留规则。
15. 预览过期后无法提交，重新预览后才能继续。
16. 映射决策只能作用于该预览列出的同名候选；预览、组织或目标节点变化后决策失败。
17. 超过单页上限的成员快照完整生成托管预览，循环游标失败关闭。
18. 托管提交投影失败后阻止同来源的新预览和新提交，恢复完成后才重新开放。

## 23. 待技术设计确认

以下事项不改变本 PRD 的产品语义，在技术设计阶段确定具体实现：

- 现有 `auth_identities` 与 `external_identity_bindings` 的最终表结构和迁移顺序；
- 企业微信部门树所需的具体接口组合和最小授权范围；
- 供应商租户稳定 ID 的规范化和来源接管验证契约；
- 对账新鲜度、离职宽限期、负缓存和熔断阈值的默认值；
- 来源级互斥采用数据库 advisory lock、任务租约或其他持久化方案；
- 人员合并能力未来的资源迁移范围和审批流程。
