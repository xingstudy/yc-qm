# 使用量 Dashboard 实现设计

本方案基于已经确认的[产品需求](usage-dashboard-prd.md)。统计范围、刷新策略和持久化故障时的可用性取舍均已确认，功能已在 `codex-usage-dashboard` 分支实现。本地验证和限制见[验收记录](usage-dashboard-validation.md)。

## 现有代码的复用边界

- 复用[用户和组织树模型](../src/organization/organization-store.ts)、[Project 作用域映射](../src/projects/project-store.ts)以及组织管理员权限。
- 复用[现有用量字段](../src/sessions/session-store.ts)作为采集输入，但保留采集来源和粒度，不能将模型请求记录行数直接视为模型调用数。
- 改造各 harness 和辅助调用的计量出口，覆盖主模型、子代理、自动任务、摘要、记忆及其他系统辅助处理；明确每条数据是否已经包含子调用的消耗，防止重复相加。
- 不将现有 Metrics 最近样本、滑动预算记录或会话请求表作为永久用量事实的来源。它们可以继续承担已有用途，未完成采集的旧记录只能用于有限回填。
- 复用[Postgres 连接与事务基础](../src/persistence/pg-pool.ts)，新模型遵守数据库迁移、插件边界和多实例约束。

## 存储与汇总

### 人工请求与任务

用户请求和任务维护独立身份、发生时间、执行状态及原始归属。人工请求复用入口的稳定幂等信息去重，内部自动重试关联同一逻辑请求；实际执行的 run 和 attempt 作为关联字段，不能仅依赖会话或会话创建者归因。

用户请求数、活跃用户和成功／失败／取消次数从这个层次计算，不从模型用量明细的行数计算。自动任务及系统辅助处理不能增加人工用户请求数。

### 永久用量事实

每条计量事实保存以下信息：

- 独立计量身份、逻辑请求／任务身份、run、attempt、调用或汇总粒度、父子关联、模型和采集来源。
- 发生时间、记录时间、原始来源及状态；迟到补录仍按实际发生日期统计。
- 组织、实际用户或责任人、Project、发生时主部门和组织层级，以及历史显示名称。
- 输入、输出、缓存读写 Token、参考费用、费用来源、估算状态、计量覆盖与缺失标记。
- 组织凭据、个人凭据或订阅授权分类，不保存密钥或授权秘密。

计量事实与会话内容生命周期分离，删除会话不会删除统计事实。已记录事件使用数据库唯一约束与事务去重；不能仅靠 leader 或进程内 Map 防重复。

不同 harness 对输入与缓存的包含关系不同。规范化时应明确包含关系，避免将已包含的缓存 Token 再加一次；不能统一假设总 Token 等于所有原始字段之和。SDK 返回的整个任务汇总与已经记录的细分调用不能重复计入组织总量。

### 持久化汇总

后台按新增事实及修正记录增量维护 Postgres 统计，保存处理进度，支持在多实例和重启后继续处理。更正采用可追溯的版本或补偿方式，汇总与处理进度在事务中一致推进，避免崩溃后重复累计。

按日保存可组合的用户、Project、部门、模型、任务来源和授权分类关系，支持组合筛选。各维度独立总计不能代替这些关系，也不预先生成所有可能筛选组合的完整统计立方体。

请求、模型调用、Token 和费用可以在对应粒度上累计。活跃用户按所选范围和筛选条件去重，不能把每日活跃用户相加；请求状态变化也不能新增一条已完成请求计数。

后台更新频率与页面每 5 分钟刷新独立。具体批量大小、处理间隔、索引和缓存参数在代表性数据与并发验证后确定，不将页面刷新间隔解释为端到端新鲜度保证。

## 查询与页面

- 页面位于管理后台，服务端校验组织管理员身份和组织边界，不能只依赖前端隐藏入口。
- 所有总览、趋势、排行、明细、对比和导出使用相同的日期和筛选解释。同一维度多选采用并集，不同维度之间采用交集。
- 日期输入包含起止自然日，内部转换为北京时间起日零点至结束日期次日零点的半开区间。按自然周、自然月分组，但只累计范围内的数据，标记不完整分组。
- 上期为紧邻之前的等长日期范围；上期为零或数据不完整时，不显示误导性的增长百分比。
- 总览、趋势和排行读取持久化统计，明细采用有界分页。排序与分页保持稳定，不用截断的近期明细计算总体。
- 费用显示已知参考金额和覆盖情况。缺失不是零；Token、调用数及费用的完整性分别展示，不共用一个笼统的覆盖百分比。
- 当前时段仅在可见页面每 5 分钟轮询；历史范围手动刷新。相同查询避免请求重叠，失败时退避，旧数据保留时仍显示刷新失败及数据截至时间。
- 日期、粒度和维度变更后立即请求新结果；旧响应不能覆盖新筛选条件。原有窗口焦点刷新应与 Usage 轮询协调。
- 历史回填或更正会使旧范围的统计版本变化，历史缓存也需要失效。缓存完整包含权限、组织、筛选条件、粒度、时区及统计版本，进程内缓存只作可丢弃优化。
- CSV 导出遵守相同权限、口径和数据版本，处理单元格公式解释风险，并记录导出审计；不能在普通页面刷新中生成全部导出内容。

## 参考定价配置与历史补估（已实现）

2026-10-14 确认提供官方默认单价及组织管理员覆盖价，仅用于参考成本估算。参考价格独立于模型启用与连接验证，按供应商、实际模型及适用服务条件匹配，区分输入、输出和缓存等单价；配置、版本及修改审计持久化到 Postgres。

价格按生效时间适用于新的使用量，并在计量时保留估算来源、适用条件与价格版本；可靠 SDK 金额继续保留，不在前端根据总 Token 和最新单价回算历史。官方默认价格随系统更新维护，不覆盖管理员自定义价；历史补估或纠错另行预览确认，缺少模型或计量条件时仍保持未知。

现有部分模型配置已支持四项价格与上下文档位，可复用校验与审计模式，但不具备覆盖所有已有模型或保留生效版本的合约。详细约束见[展示改版草案](usage-dashboard-ui-redesign.md)，历史价格取舍见[定价决策](adr/0003-version-reference-prices.md)。

## 历史回填

只回填仍存在且具有来源依据的记录。保留可追溯的原记录身份，重复执行不重复计量，实时采集与回填不重复入账。

旧记录无法确认的用户、部门、Project、费用或采集粒度分别保留未知标记。存在模型或任务级汇总时保留原粒度，不编造细分调用；没有可靠模型调用次数时，该指标显示未知。

历史名称没有可靠来源时显示现有名称并说明无法还原，不伪造发生时名称。新采集的数据保存发生时名称。

## 计量故障的行为

已确认以计量可追溯为优先：

- 发起新的模型调用前，先持久化最小计量意图；无法持久化时排队等待或明确失败，不继续发起无法追踪的模型请求。
- 发生真实消耗后写入失败，重试计量写入或汇总处理，不因计量故障重新调用模型。
- 恢复后从已持久化的请求、执行状态和可靠来源补录。没有可靠的响应或 usage 来源时仍标记缺失，不能宣称所有进程崩溃下都能恢复精确 Token。
- 汇总落后或采集存在缺口时展示待处理／数据不完整及对应时间，查询失败不返回伪造的零统计。

这意味着在模型可用但用量数据库不可用时，新的模型任务也可能等待或失败；这一可用性取舍已确认，并记录在[计量可追溯优先决策](adr/0002-prioritize-usage-traceability.md)。

## 验收重点

- 同一请求自动重试仍计一次人工请求，各次资源消耗不丢失或重复；父子用量、SDK 汇总及细分记录不重复累计。
- 删除会话、Project 或用户离职后历史计量保留；调部门和移动部门后历史归属不变化。
- 一个用户连续多天使用，周和月活跃用户仍只计一个；多部门、多 Project 及组合筛选合计符合归属口径。
- 日期边界、周一分组、跨月范围、部分周期和上期对比与明细及 CSV 一致。
- SDK 费用、估算费用和未知费用可区分；订阅消耗不解释为额外付款。
- 采集异常、数据库写入失败、重启、多实例重复投递、迟到更正及重复回填有明确处理与覆盖提示。
- 隐藏或离开页面停止轮询，恢复页面不产生请求风暴，旧响应不能覆盖新筛选；统计更新独立于页面是否打开。
- 使用代表性数据执行查询计划和并发验证，记录延迟、数据库负载和汇总落后程度。功能实现前不宣称性能已经达标。

## 验证与交付范围

实现覆盖独立计量账本、增量日汇总、各 harness 与辅助调用、后台页面和 CSV 导出。后台每 10 秒处理最多 250 条历史来源记录和 500 条待汇总事实；页面刷新间隔为 5 分钟，两者独立。汇总处理、处理进度和完整性计数在同一事务中推进。发布与合并需另行执行交付流程。

## 实现顺序

1. 建立独立请求／任务身份、永久计量存储、归属快照和计量故障处理，验证幂等、重启与多实例行为。
2. 接入各 harness 和辅助模型调用，规范化 Token、费用、授权分类与父子汇总关系，验证失败、取消和重试覆盖。
3. 建立持久化增量汇总与统一查询口径，完成日期、组合筛选、活跃用户去重、上期对比和数据完整性展示。
4. 在管理后台增加 Usage 页面、排行、明细、CSV 导出及可见页面刷新策略，验证权限和实际页面行为。
5. 执行可重复的历史回填，核对汇总与明细，使用代表性数据验证查询与并发成本，并记录已知历史缺口。

## 历史未知费用补估

2026-10-14 用户确认新模型补充价格后的历史补估方式：选定历史记录模型、日期范围及价格版本，先预览再确认。预览不改变账本，区分可补估、已有金额、未完成、模型身份不明确或不匹配、服务条件未知及 Token／单价不足的记录。仅成本未知且条件明确的记录可补估；Token、归属、已有 SDK 金额与历史估算保持原值。

补估可显式使用选定价格版本估算其生效前的未知费用，不改变价格版本对新调用的生效规则。预览固定当时记录集合与价格快照，15 分钟有效，单次最多 10000 条未知费用记录。Postgres 事务确认时锁定记录并检查是否变化；变化则要求重新预览，重试确认保持幂等，失败回滚全部改动。原费用状态、价格快照、操作者及确认时间永久保留，日汇总通过既有增量机制更新；费用趋势和覆盖率随后反映补估结果。

在新增身份字段之前产生的历史记录，可能没有可靠供应商、实际模型或服务条件。当前模型目录不能证明其发生时的路由，因此这些记录仍显示未知；首版不提供猜测模型映射或凭当前配置自动回写历史的功能。已知费用纠错或按不同价格重估不包含在本次补估入口中。
