# 使用量 Dashboard 需求

状态：需求已确认，功能已在 `codex-usage-dashboard` 分支实现。本文记录已确认的产品口径；验证证据和实际限制见[验收记录](usage-dashboard-validation.md)。

## 已确认需求

- 永久保留必要的使用量明细及归属，支持汇总和追溯；会话删除、用户离职和 Project 删除不删除用量记录。聊天正文和 Prompt 不纳入永久用量记录。
- 首版指标包括活跃用户、用户发起的请求数、模型调用数、输入 Token、输出 Token、缓存 Token、费用及成功与失败次数。
- 用户请求和模型调用分别计数；未取得费用时展示“未知”，不解释为零费用。
- 支持组织总体、用户、Project 和部门维度。
- Project 按使用发生时的实际上下文归属，其他使用归入“无 Project”；不将 Project 成员的全部个人使用量相加。
- 部门按发生时的主部门及当时的组织层级归属，上级部门可汇总子部门。多部门成员只计入主部门，没有主部门时归入“未分配”。
- 时间范围与汇总粒度分别选择，支持自定义起止日期。
- 快捷时间范围包括今天、最近 7 天、最近 30 天、本月和上月；最近 7 天包含今天。
- 汇总粒度包括日、周和月，默认按北京时间划分自然日。
- 首版位于管理后台，由组织管理员查看全部用户、Project 和部门的数据。
- 人工请求、自动任务、系统辅助处理的资源消耗全部计入，分别展示来源。有明确责任人和 Project 的按其归属，其余归入“系统／未分配”；活跃用户和用户请求数只统计人工使用。
- 同一用户请求发生自动重试仍算一次用户请求，各次实际模型调用及消耗分别记录。请求结果分为成功、失败和取消；失败前已经产生的消耗也计入，缺失数据标为未知。
- 费用以 USD 展示参考金额，标记 SDK 返回或模型价格估算等来源及估算状态，展示已知费用合计和费用数据覆盖率。费用不代表实际供应商账单。
- 2026-10-14 确认新增参考定价配置：提供供应商官方 API 默认单价，组织管理员可修改适用模型的 Token 单价；仅用于参考成本分析，不新增内部结算或实际扣费。订阅使用可显示 API 等价估算，不解释为额外付款。
- 参考单价按版本与生效时间保留，管理员改价默认只影响生效后的使用量；历史补估或纠错另行预览确认，不静默重算历史。
- 首版官方默认价格随系统更新维护，显示来源及核对日期，管理员可手动修改和恢复默认；默认价格更新不覆盖管理员自定义价。自动检测官方改价与确认同步不纳入首版。参考价格与历史未知费用补估已实现，验收记录见使用量 Dashboard 本地验收文档。
- 支持组织凭据、个人凭据和订阅授权分类；订阅 Token 消耗不直接解释为额外付款。
- 尽可能回填仍存在且能够归属的历史记录，显示覆盖范围和缺失情况。无法确认的历史归属归入“历史归属未知”，不套用当前部门、不把缺失解释为零。
- 页面提供总览指标、时间趋势、维度排行和明细，用户、Project、部门、模型和任务来源可组合筛选。所有区域使用相同筛选条件。
- 历史对象保留发生时名称，并标记已离职、已删除等状态。
- 自定义日期包含起止两天的完整北京时间自然日。自然周从周一开始；按周或月汇总时仅计入所选日期范围内的数据，并标记不完整周期。
- 支持按当前筛选条件导出汇总和明细 CSV，包含费用来源、缺失标记和历史归属，导出权限沿用组织管理员权限。
- 支持与紧邻之前的等长时段对比，展示请求数、活跃用户、Token 和参考费用变化；有缺失时提示对比不完整。
- 后台独立增量更新，当前时段的页面默认每 5 分钟自动刷新，仅在 Dashboard 可见时执行。隐藏或离开页面时暂停，历史范围手动刷新，并提供自动刷新开关和数据更新时间。
- 持久化异常时优先保证用量可追溯：模型调用前保存最小计量信息，保存失败则等待或明确报错。真实消耗发生后只重试计量写入，不重复调用模型；恢复后尽可能补录，无法恢复时明确标记缺失。

## 代码事实与设计约束

- [现有用量模型](../src/sessions/session-store.ts)提供输入、输出、缓存 Token 和费用字段，但不同 harness 的计量粒度与覆盖范围不一致。
- [会话存储](../src/sessions/postgres-session-store.ts)在删除会话时删除对应的模型请求用量，不能直接作为永久用量记录。
- [预算存储](../src/ratelimit/postgres-budget.ts)会清理滑动窗口之外的数据，不能作为永久费用历史。
- [现有 Metrics 接口](../src/api/routes/admin/observability.ts)主要用于性能分析，只扫描有限的近期样本，不是完整的长期用量汇总。
- [现有管理页面](../plugins/admin/public/index.html)没有周期性自动刷新；窗口重新获得焦点且数据超过 60 秒时会重新请求。页内 dataCache 命中后仍会发起请求，不能作为减轻服务器查询的依据。
- [组织关系](../src/organization/postgres-organization-store.ts)及 [Project 成员关系](../src/projects/project-store.ts)保存当前状态，不能直接表达发生时归属。
- [Codex harness](../src/harness/codex-harness.ts)中的费用字段固定为零，不能据此断言实际免费。
- 已删除或从未采集的历史用量无法恢复；回填必须说明覆盖范围、缺失与归属可信度。
- 用量持久化需要适应 Postgres、蓝绿运行及多实例，避免重复计量和进程退出导致的数据丢失。

## 刷新与查询设计

刷新策略已经确认，下面是据此提出的实现约束；不表示已完成实现或已通过性能验证。

- 将页面刷新频率与后台统计更新频率分开：后台按新增计量事实增量维护持久化统计，页面读取统计结果，不因打开页面而重新处理全部历史明细。
- 当前时段每 5 分钟自动刷新，仅在 Dashboard 处于可见状态时执行；隐藏、离开页面时停止轮询，恢复可见时按数据新鲜度补充刷新。历史时段不自动轮询，支持手动刷新以查看回填或修正结果。
- 提供手动刷新和自动刷新开关，展示统计更新时间、采集异常和待处理状态。页面刷新间隔不等于采集到可见数据的端到端延迟。
- 总览、趋势和排行按日期范围、权限及维度读取经过索引和汇总的数据；明细按需分页，导出单独执行，避免每次刷新同时下载全部明细。
- 同一筛选查询最多保留一个在途请求；日期或维度切换时取消或忽略旧查询，轮询失败时退避重试，避免请求重叠。暂停轮询时也应处理现有窗口焦点刷新逻辑，防止额外触发。
- 共享统计结果及重算协调须适应多实例；缓存标识必须包含组织、授权范围、完整筛选条件、粒度和统计版本。进程内缓存只能作为可丢弃的优化。
- 按日汇总可以支持日、周和月的加总，但活跃用户必须跨日去重，不能直接相加每日活跃用户数。维度组合须保留可组合关系，不能只保存彼此独立的维度总计。
- 迟到记录、失败修正和历史回填可更新旧时段；历史查询缓存需要版本校验或失效机制，不能将过去日期视为永不变化。
- 在代表性数据规模和并发量下验证查询计划、响应耗时及数据库负载，再确定缓存、汇总更新频率和索引；目前未做性能压测。
