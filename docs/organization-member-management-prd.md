# 组织成员管理 PRD

## 文档状态

- 状态：Draft
- 版本：1.0
- 日期：2026-08-27
- 关联设计：[`organization-skill-authorization-design.md`](./organization-skill-authorization-design.md)

本文档定义组织成员主数据维护、成员生命周期和批量管理能力。文中的“必须”表示产品、安全或数据一致性要求；“建议”表示实现可以调整，但调整后仍需满足验收标准。

## 1. 背景

当前分支已经提供组织节点、节点成员关系、访问组及 manager 角色维护，但成员本身仍然只有有限的身份字段，管理页面主要展示 `principalId`。管理员可以把一个已存在的用户加入组织节点或访问组，却不能完整查看和维护姓名、职务、手机、主部门等成员资料。

当前 Admin 的 `Users` 页面从会话、管理员授权、IM 绑定等运行数据汇总用户，服务目标是排障和使用情况管理，不是组织成员主数据。组织成员管理必须以持久化的 `organization_users`、`org_unit_members` 和 `access_group_members` 为权威来源，不能复用运行数据拼出事实。

## 2. 产品目标

### 2.1 第一阶段目标

- 提供独立的“组织成员”管理页面。
- 展示并维护成员姓名、企业邮箱、职务、工作手机和员工编号。
- 明确一个主部门，可同时保留其他组织节点成员关系。
- 从成员视角统一查看和维护组织节点、访问组及角色。
- 支持成员搜索、筛选、分页和详情查看。
- 支持暂停、恢复和离职，并保证旧会话和权限立即失效。
- 保证管理员维护的成员资料不会在后续登录时被身份提供方静默覆盖。
- 所有成员资料、组织关系和状态变更都有持久化审计记录。

### 2.2 第二阶段目标

- 支持组织成员 CSV 导入预检查与确认提交。
- 支持导出当前筛选结果和完整组织成员清单。
- 支持批量修改资料、主部门、其他组织节点、访问组和状态。
- 批量任务及逐行结果持久化，可以刷新页面后继续查看。
- 批量授权相关变更在一个组织事务中完成，并只递增一次组织授权 revision。

## 3. 非目标

本 PRD 明确不包含：

- 企业微信式“待激活成员”列表、未加入提醒、微信邀请或二维码邀请。
- 邮件邀请、邀请链接、重发邀请、撤销邀请等账号开通流程。
- 在 Admin 页面创建新的登录账号或手工绑定 OIDC 身份。
- 企业微信、Slack、钉钉或 SCIM 持续目录同步。
- 头像、直属上级、入职日期、语言、时区和自定义字段。
- 性别、生日、身份证等没有明确业务用途的敏感资料。
- 物理删除成员、成员审计记录或成员历史资源。
- XLSX 导入导出；第二阶段只支持 CSV。

现有 `invited` 状态为登录准入兼容状态，后端可以继续识别，但本期 UI 不提供邀请、待激活统计或 `invited` 状态操作。新增登录主体仍按现有登录准入策略进入 `organization_users`。

## 4. 术语与权威数据源

### 4.1 组织成员

`organization_users` 中的人类用户记录。只有 `active` 用户可以访问业务 API、组织目录和 Skill。

### 4.2 组织节点成员关系

`org_unit_members` 中的关系，表示成员属于某个组织、部门或团队。关系包含：

- `role=member`：普通成员。
- `role=manager`：该节点及其可管理子树的负责人。
- `isPrimary=true`：该关系是成员的主部门。

每名成员最多有一个主部门。主部门可以为空，但不能指向已归档节点。

### 4.3 访问组成员关系

`access_group_members` 中的关系，用于访问授权，不代表行政部门。访问组和组织节点必须在 UI 和 API 中保持为不同概念。

### 4.4 现有 Users 页面

现有 `Users` 页面继续承担会话、使用情况、管理员授权和模拟用户等运维用途。新的“组织成员”页面不替换其数据源，也不把历史会话参与者自动写入组织成员表。

## 5. 用户角色与权限

### 5.1 组织管理员

组织管理员可以：

- 查看全部组织成员和全部管理字段。
- 编辑成员基本资料。
- 设置或移除主部门。
- 维护成员在组织节点和访问组中的关系及角色。
- 暂停、恢复或离职成员。
- 执行导入、导出和批量操作。
- 查看成员变更审计记录。

### 5.2 组织节点 manager

组织节点 manager 可以：

- 查看其可管理子树内的成员。
- 搜索其目录可见范围内的 active 用户。
- 将普通成员加入或移出其可管理节点。
- 查看姓名、职务、企业邮箱、成员状态和节点角色。

组织节点 manager 不可以：

- 编辑姓名、邮箱、手机、员工编号等成员主数据。
- 暂停、恢复或离职成员。
- 授予或移除 manager 角色。
- 修改访问组、组织树结构或主部门到其管理范围之外。
- 使用导入、导出和批量操作。

### 5.3 访问组 manager

访问组 manager 只能在其管理的 active 访问组中加入或移除普通 active 成员，不能维护成员资料、状态、组织节点或 manager 角色。

### 5.4 普通成员

普通成员不能访问 Admin 成员管理页。面向普通成员的组织目录继续由目录可见策略控制。

## 6. 成员数据模型

### 6.1 基本资料

| 字段                      | 必填 | 规则                                      | 可见范围                           |
| ------------------------- | ---- | ----------------------------------------- | ---------------------------------- |
| `principalId`             | 是   | 不可编辑的稳定标识；高级信息中展示        | 组织管理员；授权流程按需使用       |
| `displayName`             | 是   | 去除控制字符，1–200 字符                  | 按目录可见策略                     |
| `email`                   | 否   | trim、转小写、最长 254；同组织非空唯一    | 组织管理员和有目录可见权的 manager |
| `jobTitle`                | 否   | trim、最长 200                            | 按目录可见策略                     |
| `mobile`                  | 否   | trim、最长 32；允许国家码、分机和本地格式 | 默认仅组织管理员                   |
| `employeeNumber`          | 否   | trim、最长 100；同组织非空唯一            | 默认仅组织管理员                   |
| `status`                  | 是   | 见 6.3 状态机                             | 按角色返回                         |
| `lastLoginAt`             | 否   | 只读                                      | 组织管理员                         |
| `createdAt` / `updatedAt` | 是   | 只读                                      | 组织管理员                         |
| `createdBy` / `updatedBy` | 是   | 只读                                      | 组织管理员                         |
| `profileRevision`         | 是   | 从 1 开始，每次资料变更递增               | 组织管理员                         |

手机号首期不做强制 E.164 转换，避免拒绝分机和本地号码；只做长度、控制字符和空白规范化。搜索使用规范化值，展示保留用户可读格式。

### 6.2 组织关系

成员详情返回：

- 主部门：零或一个 active 组织节点。
- 其他组织节点：零到多个。
- 每个节点上的 `member` 或 `manager` 角色。
- 访问组：零到多个。
- 每个访问组上的 `member` 或 `manager` 角色。

设置主部门时必须同时保证该成员存在对应的 `org_unit_members` 关系。移除主部门只清除 `isPrimary`，是否保留普通成员关系由请求显式决定，不允许 UI 静默删除关系。

### 6.3 状态机

本期 Admin UI 支持以下产品状态：

| 当前状态        | 允许操作 | 结果                                           |
| --------------- | -------- | ---------------------------------------------- |
| `active`        | 暂停     | 进入 `suspended`，旧会话立即失效，组织关系保留 |
| `active`        | 离职     | 进入 `deprovisioned`，旧会话立即失效           |
| `suspended`     | 恢复     | 进入 `active`，保留的组织关系重新生效          |
| `suspended`     | 离职     | 进入 `deprovisioned`                           |
| `deprovisioned` | 无       | 终态，本期不能恢复为 active                    |

`invited` 不属于本期产品状态。后端为兼容现有登录准入保留相关转换，但 Admin UI 不展示邀请操作，也不能把其他状态改为 `invited`。

离职成员必须：

- 递增 `sessionVersion` 并立即拒绝旧 Portal 身份和 capability。
- 在有效授权计算中失去组织管理员、节点 manager、访问组 manager 和 Skill 使用资格。
- 从 active 成员计数、候选选择器和普通组织目录中消失。
- 保留成员记录、组织关系、历史资源和审计记录。
- 不能通过普通“恢复”重新获得旧权限。

本期不删除离职成员的历史组织关系，以便审计和数据解释；终态约束保证这些关系不会重新生效。以后若支持返聘，需要单独定义新身份或显式权限复核流程。

### 6.4 登录资料归属

首次由登录准入创建成员时，可以使用受信身份提供方的姓名和邮箱初始化空白字段。成员记录存在后：

- 登录必须更新 `lastLoginAt`。
- 登录只能填补为空的 `displayName` 或 `email`。
- 登录不能覆盖管理员维护过的非空成员资料。
- 身份提供方本次返回的邮箱继续记录在 `auth_identities.email_at_link`，用于身份审计，不直接成为成员主数据。
- 后续外部目录同步必须使用独立产品设计和显式字段来源规则。

## 7. 第一阶段功能需求

### 7.1 组织成员入口

Admin 的组织管理区域新增“组织成员”入口，组织管理员可以进入。现有 `Users` 页面保持不变，页面文案需要区分：

- Users：系统使用与运维视图。
- Organization members：组织成员主数据与组织关系视图。

### 7.2 成员列表

默认展示 `active` 和 `suspended` 成员。组织管理员可以切换查看 `deprovisioned` 历史成员。

表格列：

- 多选框预留位，第一阶段不提供批量操作。
- 姓名。
- 职务。
- 主部门完整路径。
- 工作手机。
- 企业邮箱。
- 状态。
- 最后登录时间。

列表支持：

- 按姓名、邮箱、职务、手机号、员工编号和 `principalId` 搜索。
- 按状态筛选。
- 按组织节点筛选当前节点或整个子树。
- 按访问组筛选。
- 按是否存在主部门筛选。
- 服务端游标分页，默认 50 条、最大 100 条。
- 默认按姓名和 `principalId` 稳定排序。

所有过滤必须在服务端执行，不能先返回全量成员再由浏览器过滤。

### 7.3 成员详情

点击成员打开详情抽屉或详情页，包含：

- 基本资料。
- 状态和最后登录时间。
- 主部门与其他组织节点。
- 组织节点角色。
- 访问组与访问组角色。
- 只读身份绑定信息。
- 最近成员相关审计事件。
- `principalId`、创建人、更新人和时间等高级信息。

组织管理员可以编辑基本资料。保存时携带 `expectedProfileRevision`；并发冲突返回 `409`，页面提示重新加载，不覆盖他人的新修改。

### 7.4 主部门与组织节点维护

成员详情支持：

- 设置、替换或清除主部门。
- 加入其他组织节点。
- 从非主组织节点移除。
- 在 `member` 和 `manager` 之间调整角色。

不能把已归档节点设为主部门或新增成员关系。删除当前主部门关系前必须先清除或替换主部门标记。

### 7.5 访问组维护

成员详情支持加入、移出访问组和修改角色。访问组归档后只读展示历史关系，不能新增成员。

### 7.6 组织节点和访问组详情增强

现有组织节点和访问组详情表格不再只显示 `principalId`，必须显示：

- 姓名。
- 职务。
- 企业邮箱。
- 状态。
- 当前关系角色。
- 主部门标记，仅组织节点详情显示。

手机号和员工编号不在 manager 可见的节点/访问组列表中返回。

### 7.7 状态操作

成员详情提供：

- 暂停。
- 恢复。
- 离职。

暂停和离职必须展示影响确认。离职确认至少展示：

- 当前主部门和其他组织节点数量。
- manager 角色数量。
- 访问组数量。
- 直接目录或 Skill 授权数量。
- 旧会话将立即失效且本期不能恢复的说明。

服务端必须重新计算影响并执行状态转换，不能相信前端预览数据。

### 7.8 审计

必须记录：

- 基本资料修改，包含字段级 before/after 摘要，不记录不必要的完整手机号和邮箱到普通日志。
- 主部门设置、替换和清除。
- 组织节点及访问组成员关系变化。
- member/manager 角色变化。
- 暂停、恢复和离职。
- 并发冲突、跨组织 ID 和越权写入等高风险拒绝。

资料、状态或授权关系写入与审计必须同成同败。

## 8. 第二阶段功能需求

### 8.1 CSV 导出

组织管理员可以导出当前筛选结果或全部可管理成员。导出字段：

- `principalId`
- `employeeNumber`
- `displayName`
- `email`
- `jobTitle`
- `mobile`
- `status`
- `primaryUnitId`
- `primaryUnitPath`
- `additionalUnitIds`
- `accessGroupIds`
- `lastLoginAt`

CSV 使用 UTF-8 BOM 和标准 RFC 4180 转义。以 `=`, `+`, `-`, `@` 开头的可执行表格内容必须进行公式注入防护。导出动作必须审计，不得在日志中记录导出内容。

### 8.2 CSV 导入范围

导入只更新已存在的组织成员，不创建账号、不创建 `invited` 用户、不绑定身份。

每行必须通过以下顺序唯一匹配成员：

1. 非空 `principalId`。
2. 非空且组织内唯一的 `employeeNumber`。
3. 非空且组织内唯一的 `email`。

匹配不到或匹配到多个成员时该行报错。导入不能把历史会话参与者或外部目录记录自动转成 active 成员。

导入可更新：

- 姓名、邮箱、职务、手机、员工编号。
- 主部门。
- 其他组织节点成员关系。
- 访问组普通成员关系。

导入不允许：

- 创建成员或身份。
- 授予组织管理员。
- 授予组织节点或访问组 manager。
- 改变账号状态。
- 归档组织节点或访问组。

导入只能新增、更新或移除 `role=member` 的普通关系。目标成员已经在节点或访问组中担任 manager 时，导入可以保留该关系，但不能降级、覆盖或移除 manager 角色；存在冲突时必须在预检查中明确报错。

状态和 manager 角色使用专门的批量操作，避免在普通资料导入中隐藏高风险权限变化。

### 8.3 导入预检查

管理员上传 CSV 后先创建持久化预检查任务，不直接写成员数据。预检查输出：

- 文件摘要、行数和规范化后的文件哈希。
- 新值、现值和将发生的变化。
- 重复成员、重复邮箱和重复员工编号。
- 未知或归档组织节点。
- 未知或归档访问组。
- 路径歧义和跨组织 ID。
- 无变化行、警告行和错误行数量。
- 预计受影响成员数和授权 revision 变化。

只有零错误任务可以提交。管理员修改文件后必须重新预检查，不能复用旧任务。

### 8.4 导入提交

提交时必须携带预检查任务 ID、文件哈希和预检查时的组织授权 revision。服务端重新验证：

- 任务属于当前组织和当前管理员。
- 任务未过期、未提交且文件哈希一致。
- 组织授权 revision 未发生冲突。
- 所有目标成员、组织节点和访问组仍然存在且状态有效。

提交在一个组织事务中完成。资料和成员关系全部成功后才提交；任何一行失败则整体回滚。授权相关变化整批只递增一次组织授权 revision，并写一条任务摘要审计及必要的成员级审计。

### 8.5 批量操作

成员列表支持选择当前页或当前筛选条件下的明确成员集合。首期批量操作包括：

- 设置职务。
- 设置或清除主部门。
- 加入或移出其他组织节点。
- 加入或移出访问组，角色固定为 member。
- 暂停。
- 恢复 suspended 成员。
- 离职。

批量操作必须先生成影响预览，再由管理员确认。目标集合在预览时解析为明确的 `principalId` 列表并持久化；提交时不重新按可能变化的筛选条件扩大集合。

批量 manager 授予、组织管理员授予和物理删除不在本阶段范围内。

### 8.6 持久化任务

导入和批量操作任务必须存放在 PostgreSQL 或现有 DurableMap 的持久化实现中，不能只存进程内 `Map`。任务至少包含：

- 组织、任务类型、状态和创建人。
- 输入哈希、目标成员 ID 和规范化操作。
- 预检查 revision。
- 创建、开始、完成和过期时间。
- 汇总结果和逐行或逐成员结果。
- 幂等键和失败原因。

任务状态：`previewed | running | completed | failed | expired`。重复提交同一幂等键必须返回原任务，不得重复执行。

## 9. API 要求

### 9.1 第一阶段管理 API

建议新增或扩展：

```text
GET   /v1/admin/org/users
GET   /v1/admin/org/users/:principalId
PATCH /v1/admin/org/users/:principalId
GET   /v1/admin/org/users/:principalId/impact
POST  /v1/admin/org/users/:principalId/status
PUT   /v1/admin/org/users/:principalId/primary-unit
```

组织节点和访问组关系继续复用现有 member API，但详情响应必须由服务端批量关联成员资料。

`GET /v1/admin/org/users` 查询参数至少包含 `q`, `status`, `unitId`, `includeDescendants`, `groupId`, `missingPrimaryUnit`, `cursor`, `limit`。

### 9.2 第二阶段管理 API

建议新增：

```text
GET  /v1/admin/org/users/export
POST /v1/admin/org/users/imports/preview
GET  /v1/admin/org/users/imports/:jobId
POST /v1/admin/org/users/imports/:jobId/commit
POST /v1/admin/org/users/batches/preview
GET  /v1/admin/org/users/batches/:jobId
POST /v1/admin/org/users/batches/:jobId/commit
```

所有写接口只接受 Portal 管理员身份，不接受 agent capability。跨组织或不可见目标统一拒绝，manager 请求不得通过 Admin 插件代理绕过 Core 校验。

现有 `POST /v1/admin/org/users` 邀请接口只作为后端兼容能力保留，不增加 Admin UI 入口，也不由 Admin 插件通配代理暴露。Admin 插件只转发本文列出的精确成员资料、状态、主部门、导入和批量路径。

## 10. UI 要求

### 10.1 页面布局

桌面端采用左侧组织树、右侧成员列表：

```text
组织架构                        组织成员
公司                            [搜索] [状态] [访问组]
  研发部                        姓名  职务  主部门  手机  邮箱  状态
    平台组                      张三  工程师  平台组  ...   ...   正常
  财务部                        李四  经理    财务部  ...   ...   暂停
未分配主部门
```

选择组织节点时可以切换“仅当前节点”和“包含下级”。“未分配主部门”为计算视图，不创建虚拟组织节点。

### 10.2 详情与编辑

成员详情使用抽屉或独立详情页，避免在宽表中直接编辑多种关系。危险操作与普通资料保存分开，暂停和离职使用独立确认流程。

### 10.3 空状态和错误

必须区分：

- 没有匹配成员。
- 当前节点没有成员。
- 没有主部门的成员。
- 无查看权限。
- 并发 revision 冲突。
- 批量任务部分输入无效但尚未提交。
- 数据库或授权 revision 不可用。

数据库或权限服务不可用时拒绝写入，不得回退为浏览器本地更新。

## 11. 安全与隐私

- 所有查询携带 `org_id`，所有关系验证同组织。
- `mobile` 和 `employeeNumber` 默认只返回给组织管理员。
- 面向普通用户的 `/v1/org/*` 目录接口不得因本功能自动增加手机号或员工编号。
- 搜索、分页和计数在 SQL 可见性过滤之后执行。
- 写接口校验 Content-Type、请求体大小、字段长度和控制字符。
- 导入限制为 UTF-8 CSV，最大 5 MiB、最多 5,000 行、最多 100 个字段。
- 导入导出限流，并记录操作者、组织、行数和结果，不记录文件正文。
- CSV 导出防公式注入；CSV 导入拒绝 NUL 和超长单元格。
- 资料写、状态写、成员关系写与审计同事务。
- 批量任务的持久化结果设置保留期，过期后删除原始规范化行，只保留审计摘要。

## 12. 指标

第一阶段至少记录：

- 成员列表和详情请求成功率及延迟。
- 资料更新、组织关系更新和状态变更成功/冲突/拒绝数。
- 未分配主部门的 active 成员数。
- suspended 和 deprovisioned 成员数。

第二阶段至少记录：

- 导入预检查行数、错误率和耗时。
- 导入提交成功、失败和回滚次数。
- 批量操作类型、目标数和耗时。
- 幂等重放次数和 revision 冲突数。

指标标签不得包含姓名、邮箱、手机号、员工编号或 `principalId`。

## 13. 上线与兼容

### 13.1 第一阶段

- 数据库先 expand：新增 nullable 资料字段、`profile_revision` 和 `is_primary`。
- 现有成员资料保持不变，新增字段为空。
- 不从历史会话或外部目录自动补手机号、职务、员工编号或主部门。
- 现有组织节点成员关系默认 `is_primary=false`。
- 管理员可以后续人工设置主部门。
- Admin UI 上线后再启用资料写接口。

### 13.2 第二阶段

- 先启用导出和导入预检查，再启用提交。
- 批量暂停、恢复和离职最后开放。
- 任务表和清理器先上线，任何批量入口都不能依赖进程内任务状态。
- 上线前使用真实规模的匿名化数据验证 5,000 行任务。

## 14. 验收标准

### 14.1 第一阶段

- [ ] 组织管理员能分页查看 active、suspended 和 deprovisioned 组织成员。
- [ ] 成员列表展示姓名、职务、主部门、手机、企业邮箱、状态和最后登录时间。
- [ ] 搜索和筛选在服务端完成，分页稳定且不重复、不漏项。
- [ ] 成员资料可以编辑，重复邮箱或员工编号返回明确冲突。
- [ ] 并发资料编辑使用 `profileRevision`，旧版本写入返回 `409`。
- [ ] 后续登录不会覆盖管理员维护的非空姓名和邮箱。
- [ ] 每名成员最多存在一个主部门，归档节点不能成为主部门。
- [ ] 成员详情能维护其他组织节点和访问组关系。
- [ ] 组织节点和访问组成员表显示成员资料，不再只显示 `principalId`。
- [ ] manager 只能在授权范围内维护普通成员关系，不能编辑主数据或状态。
- [ ] 暂停立即使旧会话失效，恢复后保留关系重新生效。
- [ ] 离职立即失权、从 active 目录和候选列表消失，且不能通过普通恢复重新激活。
- [ ] `invited` 不出现在本期邀请或待激活产品流程中。
- [ ] 资料、关系和状态写入均有事务内审计。
- [ ] 内存与 PostgreSQL store 行为一致。

### 14.2 第二阶段

- [ ] 导出遵循当前筛选、权限和字段可见性，并防止 CSV 公式注入。
- [ ] 导入只更新已存在成员，不创建账号、身份或 invited 用户。
- [ ] 导入预检查能发现重复、未知、归档、跨组织和路径歧义问题。
- [ ] 有错误的导入任务不能提交。
- [ ] 导入提交全量成功或全量回滚，授权 revision 整批最多递增一次。
- [ ] 批量操作先预览后提交，提交目标不会因筛选条件变化而扩大。
- [ ] 批量 manager 或组织管理员授予不在可选操作中。
- [ ] 导入和批量任务刷新页面、进程重启和多实例切换后仍可读取。
- [ ] 重复幂等提交不会重复修改数据或重复递增 revision。
- [ ] 批量任务和成员级结果均有持久化审计。

## 15. 开放问题

以下问题不阻塞第一阶段开始，但必须在对应任务开发前确认：

1. 主部门允许选择 `department` 和 `team`，还是只允许 `department`。本文默认两者均允许，根 `organization` 不允许。
2. 企业邮箱是否对组织节点 manager 可见。本文默认按现有目录可见策略返回。
3. 离职历史成员关系保留期限。本文默认永久保留，直到有独立数据保留策略。
4. 第二阶段导入是否允许清空未出现在 CSV 中的其他组织节点和访问组。本文默认只按单元格中的显式操作修改，不做隐式全量清空。
