# 使用量 Dashboard 本地验收

日期：2026-10-13。工作分支：`codex-usage-dashboard`。本记录区分本地验证与发布，不代表已合并、已完成远端 CI 或已部署生产。

## 实现范围

- PostgreSQL 永久计量事实独立于会话，保存发生时用户、Project、主部门和组织层级；删除来源不删除账本。
- 人工请求与模型消耗分别计量，覆盖 Pi、Codex、Claude、OpenCode 及辅助调用。原生 harness 保留任务汇总粒度和子调用包含关系。
- 调用前持久化最小意图，数据库异常时阻止新调用；结果写入异常只重试写入。进程消失且无可靠 usage 来源时保留待完成／缺失状态。
- 持久化日汇总、处理进度和完整性计数在事务中增量更新，多实例用数据库锁协调，并由唯一身份去重。
- 独立日期范围与日／周／月粒度、北京时间边界、自定义日期、组合筛选、范围内活跃用户去重、等长上期对比、分页明细、CSV 导出和组织管理员权限。
- 历史显示名称保留，当前停用、离职、删除和归档状态单独展示；不会用当前组织树改写历史部门。
- 可见的当前范围每 5 分钟刷新，离开或隐藏暂停，失败退避，旧响应不能覆盖新条件；历史范围手动刷新。

## 查询与并发样本

单独的合成数据库包含 20,000 条事实，覆盖 30 天、150 名用户、20 个 Project、部门及 4 个模型。刻意采用高组合基数，最终有 20,000 条日汇总，避免只在高度压缩的小汇总上验证。

完整报表包含总览、上期、时间趋势、排行和数据状态，8 个查询同时执行：

| 查询                             | 本地延迟范围   | 已知调用 | 待汇总 |
| -------------------------------- | -------------- | -------- | ------ |
| 最近 7 天                        | 362–589 ms     | 4,662    | 0      |
| 30 天、按月、Project 排行        | 1,342–1,515 ms | 20,000   | 0      |
| 30 天、部门 + Project + 用户组合 | 39–47 ms       | 7        | 0      |

最近 7 天的日期范围查询计划使用 `usage_daily_day` 索引；单个输入 Token 汇总查询的 PostgreSQL 执行时间为 13.895 ms。这是单项 SQL 的观测，不是完整 API 的延迟。

验证期间发现数据状态提示会扫描全部历史汇总，已改成后台事务维护持久化计数。上述完整报表延迟为修正后的结果。

样本反映当前本地硬件和负载，不是生产容量保证。增加历史量和并发后仍需观测数据库负载、汇总积压及查询延迟。排行最多 200 项、筛选项最多 1,000 项、单次 CSV 最多 100,000 条；过大的导出明确报错并要求缩小范围。

## 历史与费用限制

回填只覆盖仍存在的旧用量来源。旧记录没有可靠的实际用户、部门、模型调用次数或授权信息时，分别保留未知；未知费用与已知零费用分开。自定义模型缺少价格、订阅授权缺少账单依据时，不编造 USD 金额。

后台汇总可能落后于明细；页面展示更新时间和待汇总数量，不会宣称明细与汇总在存在积压时完全同步。事实、单次报表和单次导出各自保持数据库事务一致性。
